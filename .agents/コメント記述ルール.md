# コメント記述ルール

Lua のコメントと LuaDoc アノテーションに関する補助ルールです。コメントはコードから自明でない意図・制約・例外を伝えるために使います。

## 基本

- コメントは簡潔な日本語で書き、文末は「。」で統一する。
- コードをそのまま説明するコメントではなく、理由、前提、制約、互換性、例外を書く。
- 実装変更時はコメントとアノテーションも更新し、古い説明を残さない。
- 不要になったコードをコメントアウトして残さない。
- 空のファイルヘッダーや、内容のないコメントは追加しない。

## ファイル・クラス

ファイルの責務がコードだけでは分かりにくい場合、冒頭に概要を書く。

~~~lua
--[[
    Hand.lua
    @desc 手牌の状態を保持するオブジェクト。
]]
~~~

クラスには @class、公開フィールドには @field を付ける。

~~~lua
---@class Hand 手牌の状態を保持するオブジェクト。
---@field tiles number[] 手牌の牌。
---@field riichi boolean リーチ状態。
~~~

## 関数

関数の直前に、動作を表す短いコメントを書く。公開関数や型が推測しにくい関数には、引数と戻り値を LuaDoc で明記する。

~~~lua
---牌を捨てる。
---@param index number 捨てる牌のインデックス。
---@return number|nil tile 捨てた牌。
function Hand:discardAt(index)
~~~

- @param は引数名、型、意味の順に書く。
- @return は型、必要なら戻り値名、意味の順に書く。
- 複数の戻り値は、それぞれ別の @return にする。
- nil を返し得る値は Type? または Type|nil で表す。
- 配列は number[] のように要素型を明記する。
- 型が複雑な table は table で済ませず、必要に応じて @class で構造を定義する。
- 引数や戻り値の意味が明白でも、公開 API の型情報は省略しない。
- private な小関数は、型推論で十分ならアノテーションを省略してよい。

## 列挙値・定数

列挙テーブルには @enum を付け、列挙型の用途を説明する。

~~~lua
---@enum PLAYER_ID プレイヤー ID。
local PlayerID = {
    HUMAN = 1, -- 人間プレイヤー。
    CPU = 2,   -- CPU プレイヤー。
}
~~~

値のインラインコメントは、名前だけでは意味や特殊な値が分からない場合に限る。定数一覧の各値を機械的に説明しない。

## 型と実装の一致

- アノテーションの型名は実際のクラス名・列挙名・戻り値と一致させる。
- optional、配列、複数戻り値、nil の可能性を実装と一致させる。
- 型を断定できない場合に、IDE 警告を消す目的だけで誤った型を書かない。
- アノテーションを追加・変更したら、呼び出し元と戻り値の実態も確認する。
