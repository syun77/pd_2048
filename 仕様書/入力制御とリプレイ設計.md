# 入力制御とリプレイ設計

## 目的

実機入力、自動プレイ、リプレイイベントを`GameController`で受け付け、ゲーム操作を論理コマンドへ変換して共通のゲームロジックへ渡す。入力源の選択は`GameController:update()`が行い、実機入力ではPlaydateのボタン API を直接参照する。

## モジュール

- `pd_2048/source/input/input_command.lua`: 論理コマンドを定義する。
- `pd_2048/source/input/auto_player.lua`: 自動テスト用の論理入力生成器。
- `pd_2048/source/input/replay_controller.lua`: ターン単位の圧縮履歴を記録し、一覧インデックスと個別リプレイを管理する。
- `pd_2048/source/game/game_random.lua`: ブロック生成専用の決定的乱数系列を管理する。

`input_history.lua`と`input_controller.lua`は補助コードとして存在するが、現行のゲーム進行、リプレイ記録・再生、自動プレイでは使用しない。実機入力は`GameController:update()`、自動プレイは`AutoPlayer:poll()`、リプレイは`ReplayController`のイベント列からそれぞれ処理する。DROP、HOLD、左右移動、REWINDの実行は可能な範囲で`GameController:executeCommand()`へ集約する。

## 自動プレイモード

OS のシステムメニューに `Auto Play` のチェック項目を追加し、チェック状態を `autoPlayEnabled` に保持する。`game_config.lua` の `SHOW_AUTO_PLAY_MENU_ITEM` が `true` の場合だけ、開発用に `Auto Play` 項目を表示する。ON の間は通常の実機入力を停止して `AutoPlayer` を使用する。`Retry` 実行時には `AutoPlayer:reset()` を呼び、列選択状態を初期化する。

自動プレイ開始時は最初にHOLDし、その後はマージ可能な落下候補を優先して選択する。

同値マージ可能な候補がない場合は、落下先に現在ブロックの2倍以上のタイルが接続する候補を選択する。候補が複数ある場合は、最小の上位値（例：16なら32、32がなければ64以上）を優先し、同値ならカーソルから近い列を選ぶ。

自動プレイヤーは毎手、次の優先順位で判断する。

1. 現在ブロックを各列へ落とした候補を調べ、マージ可能な候補があれば選ぶ。
2. 現在ブロックにマージ先がなく、HOLD中ブロックにマージ可能な候補があれば `HOLD` を選ぶ。
3. マージ可能な候補がなければ、接続可能な落下セルから選ぶ。

候補の順位は、現在カーソルからの距離が近い列、同距離なら左の列とする。候補生成は`MergeResolver.getAutoPlayCandidates()`から`BoardRules.findDropCell()`と既存の接続維持付きマージ判定を使用するため、通常プレイと自動プレイでルールがずれない。

## 決定性

入力だけで盤面を完全再現するには乱数系列も再現可能である必要がある。ブロック生成にはPark–Miller方式のゲーム専用乱数生成器を使用し、BGM選択などが使用する`math.random`から系列を分離する。

NORMAL開始時にseedを生成し、リプレイデータへ保存する。再生開始時は同じseedを設定してから初期NEXTキューを生成する。UNDOスナップショットには乱数生成器の内部状態も保存し、盤面・NEXT・連続出現制御と同時に復元する。

リプレイの記録・再生対象はNORMALのみとする。TIME ATTACK、CORE RUSH、PRACTICEではリプレイ記録を開始せず、保存済みのNORMALリプレイを上書きしない。

## リプレイの記録単位

生のボタン入力は保存せず、DROPまでに確定した結果を1つの`TURN`イベントとして保存する。

```lua
{
    type = "TURN",
    waitMs = 1250,
    targetColumn = 4,
    holdClass = "USED",
    holdApplications = 1,
    drop = true,
}
```

- `waitMs`: 操作可能な`INPUT`フェーズでプレイヤーを待った累計時間。`0～3000ms`に制限する。HOLD、DROP、回転、マージなどのアニメーション時間は含めない。
- `targetColumn`: DROP直前の最終カーソル列。左右入力の回数や端で無効になった入力は保存しない。
- `holdClass`: `NONE`または`USED`。各ターンは必ずどちらか一方として1回だけ集計する。
- `holdApplications`: 最終状態を作るために必要な最小HOLD回数。
- `drop`: 通常は`true`。HOLDの結果だけでゲームオーバーまたはPRACTICEクリアになった場合は`false`とする。

DROPできない列での下入力、HOLD不能時のA入力など、ゲームが受理しなかった操作は保存しない。

## 左右入力の圧縮

左右移動は相殺後の回数ではなく`targetColumn`として保存する。これにより盤面端で変化しなかった入力も除外できる。再生時は現在列から保存列まで最短経路で移動する。

たとえば境界の影響がない状態で右3回、左2回を行った場合、開始列から右へ1列の結果だけが残る。

## HOLD入力の圧縮

ターン開始時にHOLDが空でなければ交換は2回で元に戻るため、入力回数を偶奇へ正規化する。

```text
0回 → 0回
1回 → 1回
2回 → 0回
3回 → 1回
```

ターン開始時にHOLDが空の場合、最初のHOLDでNEXTが1つ進むため、正規化後の回数は最大2回になる。

```text
0回       → 0回
1、3、5回 → 1回
2、4、6回 → 2回
```

`holdApplications == 0`をHOLDなし、1以上をHOLDありとしてそれぞれ別に集計する。

## REWIND

成立したREWINDは独立イベントとして保存する。

```lua
{ type = "REWIND", waitMs = 900 }
```

Bボタンの押下列や800ms長押しは再現せず、記録した待ち時間の経過後に論理REWINDを直接実行する。REWIND前に行われ、復元によって結果が消えた左右移動やHOLDは保存しない。

## 保存と再生

通常のリプレイ再生中は、Aボタンで一時停止する。Bボタンを押しているフレームでは、現在イベントの`waitMs`待機を無視して操作または落下を開始する。落下、マージ、回転などのアニメーションは省略せず通常速度で進める。一時停止中はBボタンで再生を再開し、Bボタンを押し続けた場合は再開後すぐに待機を省略する。Aボタンでは現在地点からプレイヤー操作へ分岐する確認ダイアログを開く。

完了したNORMALプレイは、Playdate datastoreの一覧インデックス`replayIndex`と、`replay_<ID>`形式の個別リプレイへ分け、新しい順で最大30件保存する。IDは`replayIndex.nextId`から採番する8桁の10進連番とし、ローカル日時の変更や同一時刻による衝突を避ける。

`replayIndex`には`indexVersion`、`nextId`と、新しい順の一覧エントリを保存する。一覧エントリはID、`formatVersion`、`rulesVersion`、`rngVersion`、モード、保存日時、お気に入り状態、サマリーを含む。個別リプレイにはID、各バージョン、モード、seed、イベント列、最終チェックサムを保存する。一覧表示とお気に入り切替では`replayIndex`だけを読み書きし、個別リプレイは再生選択時に読み込む。一覧に対応する個別リプレイが欠損、破損または非互換の場合は再生を開始せず、インデックス更新に成功した場合は個別データを削除して該当項目を一覧から除外する。

31件目を保存するときは最も古いお気に入りでない一覧エントリを削除する。お気に入りは自動削除せず、30件すべてがお気に入りの場合は個別データを書き込まずに`REPLAY NOT SAVED`を表示する。新規保存では新しい個別リプレイ、更新後のインデックス、押し出された個別リプレイの削除の順で処理する。個別保存またはインデックス更新に失敗した場合は既存のインデックスと個別リプレイを維持する。

タイトル画面では互換性のあるNORMALリプレイが1件以上ある場合だけ`REPLAYS`を表示する。リプレイ一覧は新しい順で表示し、上下で選択、Aボタンで再生、左右ボタンでお気に入りを切り替え、Bボタンでタイトルへ戻る。お気に入りには一覧上で`assets/images/fav.png`を表示する。

一覧インデックスには次を含める。

- `indexVersion`、次回採番用の`nextId`
- 個別リプレイのID
- `formatVersion`、`rulesVersion`、`rngVersion`
- モード（NORMAL固定）
- 本体のローカル日時による保存日時（年、月、日、曜日、時、分、秒、ミリ秒）
- お気に入りかどうか
- HOLDあり・なしのターン数、スコア、到達レベル、元プレイの経過時間、結果

個別リプレイには次を含める。

- 個別リプレイのID
- `formatVersion`、`rulesVersion`、`rngVersion`
- モード（NORMAL固定）、seed
- `TURN`と`REWIND`のイベント列
- 最終盤面、NEXT、HOLD、カーソル、スコア、モード固有状態、乱数状態から計算したチェックサム

再生時は記録待ち時間、最短左右移動、最小HOLD、DROPまたはREWINDの順で処理し、各アニメーションの完了を待って次のイベントへ進む。画面左下には`TURN`イベントの現在番号と総数を`REPLAY 10/32`の形式で表示する。`REWIND`と`CHECKPOINT`は手数に数えない。Aボタンを押すと待ち時間またはアニメーションの進行中でも一時停止する。一時停止中は左ボタンで1手前、右ボタンで1手後の終了状態へ移動する。左右ボタンを長押しすると、通常カーソルと同じく初回300ms後から80ms間隔で連続して手送りする。移動先は同じseedの初期状態から待ち時間とアニメーションを省略してイベントを再適用し、対象手と次の`TURN`前までの`REWIND`・`CHECKPOINT`を適用した安定状態とする。1手目での左と最終状態での右は無視する。手送りで最終結果へ到達した場合は一時停止を維持し、A/Bボタンで結果画面へ遷移する。一時停止中にBボタンを押すと選択地点から再生を再開する。一時停止中の時間は記録待ち時間に含めない。最終チェックサムが一致しない場合は`REPLAY DESYNC`を表示する。

待ち時間は最大3秒へ切り詰めるため、再生中の経過時間は元プレイと一致しない場合がある。元の経過時間はサマリーへ別保存する。リプレイ再生ではハイスコアと最高レベルを更新しない。

## リプレイからのプレイ分岐

### 操作とダイアログ

リプレイを一時停止した状態でAボタンを押すと、盤面の上へ「プレイを再開する？」という確認ダイアログと`YES`、`NO`を表示する。初期選択は誤操作を避けるため`NO`とする。上下ボタンで選択し、Aボタンで決定する。Bボタンは`NO`と同じくダイアログだけを閉じ、同じ地点の一時停止へ戻る。ダイアログ中は手送り、再生再開、ゲーム操作を受け付けない。

`NO`ではリプレイの状態を変更しない。`YES`ではリプレイ入力を終了し、同じゲーム状態をプレイヤー入力へ引き継ぐ。確認に使用したAボタンはHOLDとして扱わず、次の新しいボタン押下から通常入力を受け付ける。最終結果へ到達済みの状態または`REPLAY DESYNC`発生後は分岐できず、従来どおり結果画面またはタイトルへ進む。

一時停止表示では操作を次のように案内する。

- `LEFT/RIGHT: STEP`
- `A: PLAY FROM HERE`
- `B: RESUME`

### 分岐地点

分岐時にseedから再構築し直さず、確認時点の盤面、NEXT、HOLD、カーソル、スコア、レベル進行、連続値制御、乱数内部状態、残りREWIND回数、UNDOスナップショット、進行中アニメーションをそのまま保持する。これにより、手送り後の安定状態だけでなく、通常再生を待ち時間、カーソル移動、HOLD、DROP、マージ、回転の途中で止めた地点からも分岐できる。

まだ適用を開始していないリプレイイベントは破棄する。すでに適用済みのカーソル移動やHOLD、受理済みDROPなどは取り消さない。アニメーション途中で分岐した場合はそのアニメーションを通常速度で完了し、次に`INPUT`へ到達してから操作可能とする。リプレイイベント番号、待ち時間基準、HOLD残回数、手送り境界、最終チェックサム検証など、再生専用の進行情報は破棄し、`REPLAY n/m`表示も消す。

### 入力源と記録資格

実装では「リプレイを自動再生中か」と「リプレイ由来で永続記録の対象外か」を別の状態として管理する。`replayMode`相当の再生状態だけを記録可否の判定に使わない。分岐後はプレイヤー入力へ切り替える一方、ラン終了まで記録資格を復活させない。

`GameController`では、既存の再生状態に加えて、少なくとも確認ダイアログの表示状態・選択値、リプレイ由来プレイかどうか、共通の永続記録資格を保持する。状態遷移は次のとおりとする。

| 現在状態 | 入力 | 次の状態 | 主な処理 |
|---|---|---|---|
| リプレイ再生中 | A | リプレイ一時停止 | 再生時刻を止める |
| リプレイ一時停止 | 左／右 | リプレイ一時停止 | 前後の手終了状態へ再構築する |
| リプレイ一時停止 | B | リプレイ再生中 | 停止時間を待ち時間から除外する |
| リプレイ一時停止 | A | 分岐確認 | 初期選択`NO`でダイアログを開く |
| 分岐確認 | Bまたは`NO`決定 | リプレイ一時停止 | ゲーム状態と再生位置を変えずに閉じる |
| 分岐確認 | `YES`決定 | リプレイ由来プレイ | 再生専用情報を破棄し、通常入力へ切り替える |

`YES`決定時は、再生フラグと一時停止フラグを解除し、ダイアログ状態、キーリピート、REWIND長押し状態をリセットする。リプレイ記録コントローラーは記録を開始・再開せず、分岐前のイベント列も渡さない。リプレイ由来フラグと永続記録資格なしの状態はゲームオーバーまたは画面離脱まで保持し、システムメニューと結果処理もこの状態を参照する。

リプレイ由来プレイではゲーム内のスコア、レベル、XP、コンボ、REWINDを通常どおり進行・表示する。実績は分岐後の確定操作から評価し、達成状態と報酬を保存する。次のその他の永続データは更新しない。

- 新しいリプレイおよび元リプレイへの追記
- ハイスコア、最高レベル、最高ブロック値、最大コンボ
- プレイ回数、プレイ時間、NORMAL履歴を含む累計統計
- NORMAL中断データ

実績判定は他の永続記録と分けた`achievementEligible`を最初に確認する。リプレイ自動再生中は無効とし、手動プレイへの分岐時に有効化する。Auto Playを1度でも有効にしたランでは、その後無効のままとする。

分岐後にゲームオーバーへ到達した場合は通常の結果画面を表示するが、新記録表示とリプレイ整合性検証は行わない。システムメニューは`Suspend`ではなく`Back to Title`を表示する。`Retry`は分岐状態を引き継がず、新しい記録対象のNORMALを開始する。

### 受け入れ条件

- 再生中のAでは一時停止だけが行われ、続くAで初めて確認ダイアログが開く。
- `NO`またはBの後は、同じ手数・同じ途中状態から手送りまたはリプレイ再開ができる。
- `YES`の決定操作がHOLDへ流れず、次の入力からプレイヤー操作になる。
- イベント待ち時間中の分岐では、そのイベントを自動適用しない。
- HOLD、DROP、マージ、回転の途中で分岐しても、受理済み処理が完了して操作可能状態へ到達する。
- 手送りした地点から分岐した後も、NEXTと乱数列、UNDO、残りREWIND回数がその地点の状態から継続する。
- 分岐後に高スコア・高レベル・実績条件を満たしても、datastoreとリプレイ一覧が変化しない。
- 分岐後は中断保存できず、ゲームオーバー後のRetryでは通常の記録対象NORMALが始まる。

### Lua実装方針

主な改修対象は次のとおりとする。

| ファイル | 改修内容 |
|---|---|
| `game_config.lua` | `YES`／`NO`選択値と中断データ形式バージョンを更新する |
| `game_state.lua` | ダイアログ、分岐ラン、共通記録資格の状態を追加する |
| `game/game_controller.lua` | 入力状態遷移、分岐処理、記録ガード、中断可否を実装する |
| `game/level_progress.lua` | レベル専用の記録資格を共通記録資格へ統合する |
| `input/replay_controller.lua` | 中断データの資格フィールドとチェックサムを更新する |
| `render/overlay_renderer.lua` | 確認ダイアログと新しい一時停止案内を描画する |
| `render/game_renderer.lua` | ダイアログを最優先するオーバーレイ順へ変更する |
| `scene/scene_game_normal.lua` | `Suspend`表示を共通の中断可否判定へ置き換える |

`scene_game_over.lua`と`app.lua`は既存経路を利用できるが、Retryと自動中断が新しい問い合わせ関数を正しく通ることを確認する。`undo_snapshot.lua`と`scene_manager.lua`は変更しない。

#### 状態の持ち方

`game_state.lua`へ次のラン状態を追加する。描画とシーンから参照する状態なので、`GameController`だけのローカル値にはしない。

| 状態 | 型 | 初期値 | 用途 |
|---|---|---:|---|
| `replayBranchDialogOpen` | boolean | `false` | 分岐確認ダイアログを表示中か |
| `replayBranchSelection` | integer | `NO` | `YES`／`NO`の現在選択 |
| `replayBranchedPlay` | boolean | `false` | リプレイから分岐したランか |
| `persistentRecordEligible` | boolean | `true` | datastoreへ記録できるランか |
| `achievementEligible` | boolean | `true` | 実績を評価・保存できるランか |

`YES`／`NO`の数値は`game_config.lua`へ列挙値として定義し、`NO`を初期値にする。`persistentRecordEligible`と`achievementEligible`はラン単位の資格であり、通常のREWINDや手送りで変化してはならないため、`undo_snapshot.lua`の保存・復元対象には加えない。`persistentRecordEligible`は新規ゲーム開始時だけ初期化し、Auto Play有効化、リプレイ再生開始、リプレイからの分岐によって`false`になった後は、そのラン中に`true`へ戻さない。`achievementEligible`は通常の手動プレイとリプレイからの分岐時に`true`、Auto Playとリプレイ自動再生中は`false`とする。

既存の`statisticsRunEligible`と`levelRecordEligible`は同じ意味を部分的に重複しているため、`persistentRecordEligible`へ統合する。`statisticsRunStarted`など、資格ではなく統計処理の進行を表す値は残す。中断データの資格フィールドと中断チェックサムも新名称へ更新し、`SUSPEND_FORMAT_VERSION`を上げる。旧フィールドを読む互換処理は残さない。

#### `game_controller.lua`

次の問い合わせ関数を追加し、シーンや将来の実績処理が内部フラグを直接組み合わせないようにする。

```lua
function GameController:isReplayBranchedPlay()
function GameController:isPersistentRecordEligible()
function GameController:canUnlockAchievements()
function GameController:canSuspendNormalGame()
```

分岐操作は次の関数へ分ける。

```lua
function GameController:openReplayBranchDialog()
function GameController:moveReplayBranchSelection(delta)
function GameController:closeReplayBranchDialog()
function GameController:branchReplayToPlayer(now)
```

`openReplayBranchDialog()`は、リプレイ再生中、一時停止中、結果未確定、再生エラーなしの場合だけ開き、選択を`NO`へ戻す。`moveReplayBranchSelection()`は`YES`と`NO`の2項目を循環させ、変更時だけカーソルSEを鳴らす。`closeReplayBranchDialog()`は盤面と再生位置を変更せず、ダイアログだけを閉じる。

`branchReplayToPlayer(now)`は次の順で処理する。

1. 一時停止開始からの時間を`startReadyUntil`へ加算し、開始演出中の停止時間を除外する。
2. `replayMode`、`state.replayActive`、`state.replayPaused`を解除する。
3. `replayData`、イベント番号、イベント開始時刻、実行中フラグ、HOLD残回数、手送り境界、再生チェックサム用状態を破棄し、`replaySaved=true`として終了時処理の再実行を防ぐ。
4. `ReplayController:cancelRecording()`を呼び、元イベント列の引き継ぎと新規記録開始を両方防ぐ。
5. `state.replayBranchedPlay=true`、`state.persistentRecordEligible=false`、`state.achievementEligible=true`を設定する。
6. ダイアログ、Auto Play、カーソルキーリピート、REWIND長押し状態をリセットする。

盤面、NEXT、HOLD、スコア、レベル、乱数生成器、UNDOスナップショット、`phase`、アニメーション用フィールドには触れない。分岐直後の`update()`はそこでreturnし、決定に使ったAを同一フレームのHOLDへ流さない。次フレーム以降、`phase`がアニメーション中なら既存の`advanceAnimation()`が完了させ、`INPUT`なら通常入力を受け付ける。

`start()`では分岐ダイアログと`replayBranchedPlay`を必ずリセットする。通常の手動プレイは`persistentRecordEligible=true`、中断復元は中断データに保存した資格、リプレイ再生とAuto Play対象は`false`として開始し、`achievementEligible`も同じ初期値にする。分岐時だけ`persistentRecordEligible=false`を維持したまま`achievementEligible=true`へ切り替える。中断復元で一時的に資格を`false`へ落としてから戻す実装にはしない。また、記録対象でない開始経路では必ず`ReplayController:cancelRecording()`を呼び、前のランの記録状態を残さない。

`update()`のリプレイ一時停止分岐は、次の優先順へ変更する。

1. ダイアログ表示中なら、上下で選択、Bでキャンセル、Aで`YES`／`NO`決定し、他の入力を処理せずreturnする。
2. 最終結果へ到達済みなら、従来どおりA/Bで結果画面への進行を許可し、分岐ダイアログは開かない。
3. 通常の一時停止なら、左右で手送り、Bでリプレイ再開、Aでダイアログを開く。

#### 永続記録の共通ガード

次の処理は`replayMode`ではなく`persistentRecordEligible`を共通ガードとして使用する。リプレイ再生中も分岐後も同じ入口で停止させる。実績だけは`achievementEligible`を使用し、分岐後に有効化する。

- `updateStatisticsPlayTime()`の総プレイ時間加算
- `recordStatisticsPlay()`、`recordStatisticsResult()`
- `saveCurrentModeHighScore()`、`applyLevelProgress()`内の最高レベル保存
- `finishMerge()`内の最高ブロック値・最大コンボ更新
- タイムアタック／CORE RUSH／PRACTICEの永続保存処理
- `suspendNormalGame()`と自動中断保存

リプレイ入力記録の`beginDecision()`、`noteHold()`、`recordTurn()`、`recordRewind()`は、記録対象NORMALかつ復元・再生中でない場合だけ呼ぶ。`ReplayController`側の`recording`判定も残し、二重に防御する。

`finishReplayRecordingIfNeeded()`は処理順を明確に分ける。リプレイ再生の完走時だけ最終チェックサムを検証し、`persistentRecordEligible=false`のプレイヤー操作ではチェックサム検証、`normalSuspend`削除、`ReplayController:finish()`をすべて行わず終了済み扱いにする。これにより分岐後のゲームオーバーで`REPLAY NOT SAVED`を誤表示しない。

#### 描画とシーン

`overlay_renderer.lua`へ`drawReplayBranchDialog()`を追加する。既存の`drawMenu()`を使い、質問文を選択対象外の先頭行、`YES`と`NO`を選択行として描画すれば、反転選択や中央配置を再利用できる。`drawReplayPause()`は案内を`LEFT/RIGHT: STEP`、`A: PLAY FROM HERE`、`B: RESUME`へ変更し、3行が収まるよう背景矩形を広げる。

`game_renderer.lua`のオーバーレイ優先順は、分岐確認ダイアログ、リプレイ一時停止、通常ポーズ、通知の順にする。ダイアログ中は一時停止案内を重ねて描かない。`replayActive=false`になるため、分岐後の`REPLAY n/m`は既存条件で非表示になる。

`scene_game_normal.lua`は、`Suspend`の表示条件を個別のモード／再生フラグ判定から`canSuspendNormalGame()`へ置き換える。リプレイ再生中と分岐後はいずれも`Back to Title`を維持する。分岐時にAuto Playを無効化した状態も反映するため、リプレイ再生状態が解除されたフレームでシステムメニューを再構築する。

`scene_game_over.lua`のRetry分岐は、分岐時に`replayMode=false`かつ`replayData=nil`とすることで既存の通常ゲーム開始経路を利用できる。ただし可読性のため、Retry判定を「リプレイを再生し直すか」「新規ゲームを始めるか」の問い合わせ関数へまとめてもよい。新規`start()`で`replayBranchedPlay`と記録資格がリセットされることを確認する。

`app.lua`の自動中断処理は既存どおり`suspendNormalGame()`を経由するため、追加分岐は不要である。`undo_snapshot.lua`、`scene_manager.lua`も動作変更は不要である。

#### 実装後の確認

`pdc`ビルド後、Simulatorでイベント待ち、カーソル移動後、HOLDアニメーション、DROP、マージ、回転、手送り後の各地点から分岐する。分岐前にdatastoreの`replayIndex`、`highScore`、`normalBestLevel`、`statistics`、`normalSuspend`を記録し、分岐後のゲームオーバーと画面離脱後も変化しないことを確認する。結果画面に`NEW BEST LEVEL`と`REPLAY NOT SAVED`が出ないこと、システムメニューが`Back to Title`のままであること、Retry後の新規NORMALでは記録が再び有効になることも確認する。

## 中断セーブ

中断セーブは永続記録資格があるプレイヤー操作中のNORMALだけを対象とし、固定datastoreキー`normalSuspend`へ1件保存する。リプレイから分岐したプレイは対象外とする。通常の`replayIndex`と個別リプレイには登録せず、最大30件の制限にも含めない。

中断データには`SUSPEND_FORMAT_VERSION`、リプレイの各互換性バージョン、モード、seed、保存済みイベント列、保存日時、永続記録資格、復元地点のチェックサムを含める。中断時にDROP前の操作が残っている場合は次のイベントを末尾へ追加する。

```lua
{
    type = "CHECKPOINT",
    waitMs = 800,
    targetColumn = 4,
    holdClass = "USED",
    holdApplications = 1,
    drop = false,
}
```

`CHECKPOINT`はカーソル位置と正規化したHOLD回数を適用するがDROPしない。中断前にHOLDを使用し、再開後にDROPした場合は、そのDROPをHOLDありのターンとして集計する。繰り返し中断しても未確定ターンのHOLD使用情報を引き継ぐ。REWINDが成立した場合は未確定ターンのHOLD使用情報を破棄する。

アニメーション中に`Suspend`を選択した場合は、SEを抑制して受理済み操作のアニメーション完了処理を実行し、次の安定した`INPUT`状態を保存する。途中フレーム、メッセージ残り時間、キーリピート、BGM・SE位置は保存しない。

`CONTINUE`では通常のリプレイ待ち時間を無視し、1フレームあたり`SUSPEND_RESTORE_STEPS_PER_FRAME`回を上限として、論理イベントとアニメーション完了処理を高速適用する。復元中は通常入力とSEを停止し、ゲーム画面を描画せずに`NOW LOADING...`だけを表示する。盤面、NEXT、HOLD、カーソル、スコア、レベル進行、連続値制御、乱数状態、残りREWIND回数、UNDOスナップショットを含む中断チェックサムが一致した後、リプレイ再生状態を解除して既存イベント列への記録を再開する。

復元成功時または`NEW GAME`選択時に`normalSuspend`を削除する。欠損、非互換、イベント適用失敗、チェックサム不一致では通常入力へ移行せず、データを残したままタイトルへ戻る。

システムメニューからホームへ戻る場合は`playdate.gameWillTerminate()`、低バッテリースリープへ入る場合は`playdate.deviceWillSleep()`から共通の自動中断処理を呼ぶ。現在のシーンがゲーム画面で、プレイヤー操作中のNORMALである場合だけ保存する。通常の端末ロックと、システムメニューを開いただけの`playdate.gameWillPause()`では保存しない。自動保存後もゲームが継続した場合に備え、ゲームオーバー、リトライ、新規NORMAL開始時には古い`normalSuspend`を削除する。
