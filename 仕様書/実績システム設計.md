# 実績システム設計

## 1. 目的と範囲

本書は、`assets/achievement/achievements.json`を正本として、アプリケーションが実績を読み込み、達成条件を判定し、達成状態と報酬を保存し、達成通知を表示するための設計を定める。

初期実装の表示文言は英語だけとする。実績一覧の日本語対応はJSONに既に存在するが、達成通知では`name.en`を使用し、空の場合だけ`name.ja`へフォールバックする。

## 2. 基本方針

- 実績IDは永続保存と内部参照に使う安定したキーとする。
- 画面上の`No`は`achievements`配列の位置を1始まりで表した表示番号とし、保存しない。
- 達成条件や報酬の意味を実績ID、名前、説明文から推測しない。
- ゲーム進行側は条件式を知らず、判定に必要な確定済みイベントだけを実績管理へ渡す。
- 実績管理は未達成の定義だけを評価し、達成済み実績を再通知しない。
- 達成と報酬は取り消さない。REWINDで盤面やラン状態が戻っても、既に達成した実績は維持する。
- 自動プレイ、リプレイ再生、リプレイから分岐したプレイなど、`persistentRecordEligible=false`のランでは評価、保存、報酬、通知を行わない。
- 中断データの高速復元中は評価しない。復元前に達成した実績は即時保存済みであり、復元完了後の新しいプレイヤー操作から評価を再開する。

## 3. コンポーネント

### 3.1 `AchievementDefinitionLoader`

`assets/achievement/achievements.json`を起動時に1回読み込み、ルートの`version=1`を確認して実行用定義へ正規化する。

実行用定義は次を保持する。

- `id`
- 配列順から生成した`displayNo`
- `name.en`とフォールバック名
- `category`
- `condition.type`、`scope`、`operator`、`params`
- `reward.type`、`reward.id`
- `hidden`、`progressVisible`

`definitions`はエディターの候補表示用であり、ランタイム機能を追加する仕組みではない。アプリケーションが実装済みのCategory、Condition Type、Scope、Operator、Reward Typeだけを受理する。不正な項目はコンソールへIDと理由を出して項目単位で除外し、ファイル全体の読込失敗では空の定義として安全に起動する。

初期実装が対応するCondition Typeは、現行18件で使う次の6種とする。

| Condition Type | 必須Params | 評価値 |
|---|---|---|
| `TILE_VALUE` | `value` | そのランで確定した最大マージ値 |
| `COMBO` | `value` | そのランの最大コンボ |
| `LEVEL` | `value` | NORMALの到達レベル |
| `CLEAR_TIME_MINUTE` | `value`, `mode` | 指定モードのクリア時間。比較時は`value * 60000`ミリ秒へ変換 |
| `PRACTICE_CLEAR_COUNT` | `all=true`、または`count` | 解放対象となる全ステージ数とクリア済みID集合 |
| `UNLOCK_ACHIEVEMENT` | `value` | 判定候補自身を含む、達成後の実績数 |

エディター候補にある未使用の`MERGE_COUNT`、`SCORE`、`CLEAR_MODE`、`NO_REWIND_CLEAR`、`PLAY_COUNT`、`TOTAL_SCORE`は、必要なラン内値・累計値・確定タイミングを別途定義して実装するまで予約値とし、実績データの保存検証では選択不可にする。

### 3.2 `AchievementStore`

datastoreキー`achievements`へ、定義とは分離した次の形式で保存する。

```lua
{
    version = 1,
    unlockedIds = {
        tile64 = true,
    },
    rewards = {
        timeAttack = { sprint64 = true },
        replay = { replay = true },
        extend = { extend = true },
        sound = { soundtest = true },
        playbook = { [1] = true },
    },
}
```

- `unlockedIds`は実績IDの集合であり、配列順変更の影響を受けない。
- `rewards`は実績定義から再計算せず、取得済み権利として独立に永続化する。定義の削除や報酬変更で、過去に取得した権利を失わせない。
- `PLAYBOOK_UNLOCK`のIDは数値化し、`PlaybookLoader.loadVisible`へそのまま渡せる集合にする。
- 1回の評価で達成した全実績と報酬をメモリ上の複製へ適用し、datastoreへの1回の書込みに成功してから現在状態を差し替える。保存失敗時は達成扱いにせず、通知も出さず、次の評価機会に再試行する。

### 3.3 `AchievementManager`

定義、保存状態、ラン内の最大値、達成通知キューを所有する。`GameController`からイベントを受け、Category、Scope、Condition Type、Operatorの順で評価する。

公開問い合わせは最低限、次を用意する。

- `isUnlocked(id)`
- `getUnlockedIds()`
- `getDefinitions()`
- `hasReward(type, id)`
- `getPlaybookUnlockNumbers()`
- `emit(event)`
- `update(now)`
- `currentNotification()`

比較演算子`>=`、`==`、`<=`、`>`、`<`は共通比較関数に集約する。Condition Typeごとに比較を再実装しない。

### 3.4 `AchievementNotificationRenderer`

`App:draw()`のシーン描画後に、現在の通知を画面最前面へ描画する。英語用デフォルトフォントを一時的に設定し、描画後に元のフォントへ戻す。

表示は画面上部の2行パネルとする。

```text
 ACHIEVEMENT UNLOCKED
 No. 05  Created a 64 Tile
```

- 位置は`x=8, y=4, width=384`を基準とし、既存HUDを一時的に覆う。
- 1件を3000ミリ秒表示する。
- 入力を遮断せず、ゲーム進行を止めない。
- 同時達成はJSON配列順でキューへ積み、1件ずつ表示する。
- シーン遷移でキューを破棄しないため、クリア直後にGAME OVERへ移っても通知を表示できる。
- `No`は2桁以上のゼロ埋めとし、実績数が100件以上なら必要桁数をそのまま表示する。

## 4. イベントと判定タイミング

### 4.1 ラン開始

`GameController:start()`で実績管理のラン状態を初期化する。保持する値は`mode`、`maxMergedTile=0`、`maxCombo=0`、`maxLevel=1`である。実績の永続状態と通知キューは初期化しない。

### 4.2 進行確定

マージとレベル計算をすべて状態へ反映した後に`RUN_PROGRESS`を送る。レベルはDROPだけでも上昇するため、DROP確定後にも送る。

```lua
{
    type = "RUN_PROGRESS",
    mode = state.mode,
    mergedTile = state.mergeValue, -- DROP時はnil
    combo = state.combo,
    level = state.level,
    eligible = game:canWritePersistentProgress(),
}
```

マネージャは最大値を更新してから、次を評価する。

- `TILE_VALUE`: Categoryが`NORMAL`かつmodeが`NORMAL`
- `COMBO`: Categoryが`MAIN_GAME`の場合はPRACTICE以外
- `LEVEL`: Categoryが`NORMAL`かつmodeが`NORMAL`

これにより回転前マージ、回転後マージ、連鎖マージのどの段階でも、値が確定した直後に達成を通知できる。

### 4.3 PRACTICEクリア

`beginPracticeVictory()`で新規クリアIDを集合へ保存した後に`PRACTICE_CLEARED`を送る。イベントには全ステージID集合とクリア済みID集合を渡す。`all=true`は、読込可能な全ステージのIDがクリア済み集合に含まれる場合に真とする。ファイル数だけの比較にせず、達成前にステージが追加された場合も追加分をクリアするまで未達成となるようにする。

### 4.4 TIME ATTACK / CORE RUSHクリア

クリア演出終了後、`state.result=VICTORY`を設定し、タイマー値が確定した時点で`MODE_CLEARED`を送る。

```lua
{
    type = "MODE_CLEARED",
    mode = state.mode,
    elapsedTimeMs = state.elapsedTimeMs,
    eligible = game:canWritePersistentProgress(),
}
```

`CLEAR_TIME_MINUTE`は`params.mode`とイベントのmodeが一致した定義だけを評価する。`TIME_ATTACK` Categoryは64、256、512の総称であり、Categoryだけでは対象モードを区別しない。

### 4.5 達成数による連鎖

通常条件で新規達成が発生した後、`UNLOCK_ACHIEVEMENT`をJSON配列順に再評価する。未達成の判定候補自身を今回達成する1件として含め、現在の達成数に1を加えた達成後件数を`params.value`と比較する。新たに達成した場合は達成数が増えるため、追加達成がなくなるまで反復する。

現行の達成数条件は5件、11件、17件である。1イベントで複数の通常実績と達成数実績が解放された場合も、全件を1トランザクションで保存し、通知は最終的な配列順に並べる。通知はキューの先頭1件だけを表示し、1件の表示終了後に次の1件を連続表示する。

## 5. Categoryとモードの対応

| Category | 対象モード |
|---|---|
| `SYSTEM` | モードに依存しない累計条件 |
| `NORMAL` | `NORMAL`だけ |
| `TIME_ATTACK` | `TIME_ATTACK`、`TIME_ATTACK_256`、`TIME_ATTACK_512` |
| `CORE_RUSH` | `CORE_RUSH`だけ |
| `PRACTICE` | `PRACTICE`だけ |
| `MAIN_GAME` | PRACTICE以外の全ゲームモード |

ScopeとCondition Typeの組合せも検証する。現行データでは`TILE_VALUE`、`COMBO`、`LEVEL`、`CLEAR_TIME_MINUTE`は`RUN`、`PRACTICE_CLEAR_COUNT`と`UNLOCK_ACHIEVEMENT`は`LIFETIME`だけを許可する。

## 6. 報酬

新規達成と同じトランザクションで報酬権利を保存する。

| Reward Type | 利用箇所 |
|---|---|
| `NONE` | 状態変更なし |
| `TIMEATTACK_UNLOCK` | TIME ATTACK / CORE RUSHの対象モード表示 |
| `REPLAY_UNLOCK` | 保存済み互換リプレイがあり、かつ`replay`権利がある場合にREPLAYSを表示 |
| `EXTEND_PLAY` | リプレイ一時停止中の`PLAY FROM HERE`を`extend`権利がある場合だけ許可 |
| `SOUND_UNLOCK` | `soundtest`権利がある場合にSOUND TESTを表示 |
| `PLAYBOOK_UNLOCK` | 取得済み番号集合を`PlaybookLoader.loadVisible`へ渡す |

報酬で閉じられないNORMAL、PRACTICE、PLAYBOOK、ACHIEVEMENTS、STATISTICSは常時利用可能とする。新規保存データでは、報酬対象機能は対応実績を達成するまで非表示とする。

TIME ATTACK系報酬の永続保存とタイトル表示制御は`AchievementStore`へ実装済みである。`sprint64`、`sprint256`、`sprint512`、`corerush2048`を`rewards.timeAttack`へ個別に保存し、1件以上解放済みの場合だけTIME ATTACKルートを表示する。実績達成による`unlockReward`呼出しは実績管理の実装時に接続する。

## 7. ACHIEVEMENTS画面への供給

本実装で一覧画面を完成させない場合でも、画面側がJSONを再読込しないよう、`AchievementManager`から定義と達成集合を取得する。

- 一覧順とNoは定義配列順とする。
- 達成済みは英語名と説明を表示できる。
- 未達成かつ`hidden=true`なら名前と説明を隠す。
- `progressVisible=true`ならCondition Typeが返す現在値と目標値を表示できる。

## 8. 現行JSONの前提

`achievements.json`は次の状態へ正規化済みであり、アプリケーション実装ではこれを前提とする。

1. ルートの定義形式は`version=1`とする。
2. PLAYBOOK報酬は`PLAYBOOK_UNLOCK`と番号`"1"`、`"2"`、`"3"`を使用する。
3. 時間実績は`params.mode`で64、256、512 SPRINTとCORE RUSHを区別する。
4. 達成数実績は候補自身を含む5件、11件、17件を条件とする。
5. エディターはCondition TypeごとのParams、Category、Scope、Reward IDを検証し、未対応の予約Condition Typeを選択候補に含めない。

## 9. 実装順

1. JSONとエディター検証を本設計へ合わせる。
2. `AchievementDefinitionLoader`、`AchievementStore`、`AchievementManager`を追加し、読込・比較・連鎖達成をゲーム非依存の検証コードで確認する。
3. `GameController`へ確定イベントの通知点を追加する。
4. 報酬問い合わせをタイトル、リプレイ分岐、PLAYBOOKへ接続する。
5. `AchievementNotificationRenderer`を`App`の最前面描画へ接続する。
6. ACHIEVEMENTS一覧へ定義と達成状態を供給する。

最低限、単一達成、同時複数達成、5/11/17の連鎖、1件ずつの連続通知、保存失敗、再起動、REWIND、自動プレイ、リプレイ、中断復元、各時間モードの取り違えがないことを確認する。
